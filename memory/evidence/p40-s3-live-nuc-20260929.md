## Plugin change: `hid-transport` (implemented, container-tested, NOT hardware-tested)

Reference: the Lenovo CLI (`IspEngine_Lib`). It chooses the HID transport for every hub with `uSupportHID > 0` in the vendor-support string (fwupd's `hid_isp`, unused so far), reads identity over plain USB descriptors, links the HID through its parent hub after a `GLI HID` token check, frames vendor requests exactly like `FuGenesysHubhidDevice` (setup in bytes 1..8, report id 0, a packed single SetFeature for small writes), and finishes with `ISP_EXIT` (`0x81` value 0). Also from the CLI: register 5 is the flash RDSR command, so a 0 only means "flash not busy"; `0x81` values are 0 exit, 1 enter, 2 switch to mask, 3 auto hot plug, 5/6 switch HS/SS.

Change in `plugins/genesys` (owner approved): private flag `hid-transport` (quirk `Flags`, only `17EF:1151`). Hub setup keeps the USB-descriptor identity part; the flash part (`ISP_ENTER`, CFI, firmware size, codesign key) moved into `fu_genesys_usbhub_device_setup_flash()`. For a `hid-transport` hub without a proxy it is marked pending and `UPDATABLE` is removed; the plugin calls `fu_genesys_usbhub_device_setup_flash_late()` right after binding the HID proxy (it opens the hub with its HID proxy and runs the flash part through the HID; success restores `UPDATABLE`, failure only logs a warning). A `hid-transport` hub with codesign is rejected. Quirks also map `17EF:F00F`, `4C41`, `4C42` to `FuGenesysHubhidDevice`. Every other hub runs the same steps in the same order as before.

Validated: Ubuntu 24.04 container (glibc 2.39) build; `genesys-self-test` 6/6 (new: `hid-transport` only on 1151, the three HID PIDs map to the hub HID type); the builtin quirk contains the new entries; the deployable tarball `fwupd-s3-ubuntu2404-20260930-hidtransport.tar.gz` (SHA-256 `1f9bd09e0ffe969c5113ead19940322914482c9e117214b2294c64859910017e`) needs at most `GLIBC_2.38`. ## Lenovo tool end-to-end update flow for the P40 hubs, versus fwupd (2026-09-30, static, no hardware)

Sources: GUI `E:\BackUp\Git_EE\lenovo_isp_tool\Source\LenovoISPTool`, CLI and library `E:\BackUp\Git_EE\cli` (`Source\Basic`, `SubModule\IspEngine_Lib`), package `C:\Users\reiko\Desktop\Backup\0317\Lenovo_ISP_Tool_P40WD-40_v0_0_0_39` (`isp_setting.json`, `updater_setting_list.json`, `TargetDevice.ini`, `Firmware\Hub\GLHub.ini`). All three hubs are non-codesign with HID ISP capability (`uSupportHID` above 0).

Lenovo timeline:
1. The GUI reads `isp_setting.json` (hub order L1, L2, L3; `forceUpdate=true`, so every hub is treated as needing an update) and starts one process per hub, awaited in turn: `GLUpdateTool_Lenovo.exe isp -id=<1..3> -p=<file>` (no `-re`, no force flag, no per-hub delay). A failure stops the remaining items.
2. The CLI locates the hub by scan order (`-id` is a 1-based index into a location-sorted list), not by VID/PID; the package-root `TargetDevice.ini` is not on the CLI file search path in this layout. It reads the USB descriptors (tokens `0x80`, `0x81/0x82`, `0x83`, vendor-support `0x86`, project `0x8A`), takes the chip from the static tool string, and links the HID of each hub because `uSupportHID` is above 0.
3. The GUI path (`GlHubCtrl::LoadBinFile`, default match mask) checks bonding and version only, not PROJECT; only the separate `ispmatch` command checks PROJECT. The package `GLHub.ini` sets `FWRecovery=1`; upgrade-only and allow-downgrade default to false.
4. ISP enter `0x40/0x81` value 1, RDSR poll `0xC0/0x82` value `0x0502`, flash ID `0x9F02` (`c8 40 12`); HID framing is 65-byte reports (report id 0, setup in bytes 1-8, payload after).
5. Bank choice (non-codesign, `FWRecovery=1`, AUTO): both banks are read and validated (XROM signature, size, checksum); with two valid banks the older one is chosen (tie: bank1); one invalid bank: that one; both invalid: both. For GL3523-50 a bank2 choice becomes copy valid bank1 to bank2, then write bank1. A target older than the running version with `FWRecovery=1` selects both banks (running bank 1: bank2 first, then bank1).
6. Per 4 KiB unit: erase (`0x40/0x83`, value `0x2001`), blank check (last 1 KiB), write, read-back compare, each up to three attempts. No commit-last marker: header first, checksum in the image tail; no rollback; interruption can leave a bank partly written.

There is no wait for re-enumeration between hubs.

- Transport: Lenovo sends vendor commands for all three hubs over HID; fwupd uses the HID proxy once bound (all hubs after the plugin binds it) and direct control transfers only during setup.

Owner supplied the Genesys protocol notes: vendor commands `0x8X` (normal) and `0xAX` (normal plus code sign); the bin moves `0xC0-0xFF` ("X Data") to the end and fills the original place with random data (the FW checksum uses the original values); "Verification Data" of `0x380` bytes (public key, signature at `+0x212`, check data, empty, X Data at `+0x340`); GL3523-50 sends firmware plus verification data as one ISP command at address 0 and stores the verification data at `CodeSize*1k`; GL3525 sends the firmware, then the verification data to flash `0x16000` (bank1) or `0x17000` (bank2); the firmware skips `0xC0-0xFF`, verifies signature and checksum and programs X Data last; the tool polls with a timeout (about 52 s on GL3525); different models must not be cross-flashed; verification exists only in GLbinTool and in the firmware.

Scope: this flow is for code-sign hubs. The P40 hubs report `HP Proprietary`/`codesign_check` 0 (non-codesign, see the codesign check above), and their payloads are exactly `CodeSize*1k` long (L3: code-size byte `0x1F` at `0xFB`, file size `0x7C00`), with no appended verification data. In the L3 flash dump every slot's stored sum16 equals the sum of the actual bytes (including `0xC0-0xFF`), so the X Data range holds its original values in place, as expected for the non-codesign layout.

Comparison (static):
- fwupd, code-sign hubs: request numbers follow (`0xA1/0xA2/0xA3` when the vendor-support field is above 0). Not implemented: sending the key or signature first when the flash has none (setup requires a parsable key already in flash), moving, skipping, restoring or last-writing X Data, the `0x380` layout (fwupd parses RSA `N/E` plus a 256-byte signature, or ECDSA hash, key and signature, as separate images), a merged GL3523-50 command (main and code-sign images are written separately), and a long verification wait (the hardware check is a single request with a 5 s USB timeout, and its request `0xAC` is commented as GL3590). The code-sign bank addresses match the notes for GL3525 (`0x16000/0x17000`); GL3523-50 uses fixed `0x7C00/0xFC00`, which equals `CodeSize*1k` only when the code size is `0x1F` KiB.
- Lenovo CLI, code-sign hubs: request numbers follow; it knows the X Data range (`0xC0`, `0x40` bytes) and the `0x380` blob constants, restores X Data into a temporary image for the host-side RSA check, and polls the hub for the X Data signature result with a 60 s timeout. Not found: host-side check-data (checksum-8 XOR project string) computation, a skip or last-write of `0xC0-0xFF` in the writer, or sending a missing key first on the HID-RSA path. The spec text was not in the CLI `Doc` folder.
- Non-codesign hubs (the P40 case) in both tools: the image is written in address order with no special handling of `0xC0-0xFF`, no random fill and no verification data. fwupd rejects cross-model flashing only through the P40 strict PROJECT and mask-IC check; the Lenovo default match checks bonding and version.

Conclusion: neither tool implements the notes as written for code-sign hubs, but those steps do not apply to the three P40 hubs; for them both tools follow the plain non-codesign flow. Not established: what the hub firmware itself does with `0xC0-0xFF` on a non-codesign hub, and any behaviour on hardware.
